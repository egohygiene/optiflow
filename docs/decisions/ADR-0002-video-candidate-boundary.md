# ADR-0002 — Bound development video candidates without collection mutation

November 12 proposed MP4 extension: a distinct H264/AAC delivery profile admits
larger explicitly bounded files through descriptor-bound hashes/range reads and
independent ISO sample-table/clock/audio/metadata observation. Historical FFV1
profiles and default observation ceilings do not widen. Container declarations
are not native codec/decode or perceptual acceptance. Later lossy processing
must preserve originals and separate structure, actual byte caps, independent
decode, human review and release/native qualification. No source replacement,
disposal, second orchestration engine or automatic Flow placement is authorized.
This remains proposed and unqualified.

The MP4 read-only plan binds explicit CRF/preset or target-byte choices to exact
source/provider identities and whole-work admission. Target allocation preserves
copied audio and an explicit metadata/mux budget; two-pass bitrate is intent,
not a guaranteed size or quality claim. Invalid budgets refuse without silent
trimming, resizing or audio re-encoding. This source extension remains proposed.

MP4's separately named sandbox policy reuses the same launch, cgroup/tmpfs
observation and bounded subprocess owner, with explicit longer elapsed/larger
scratch admission. A closed internal worker keeps two-pass logs in one session
and frames actual child/job/output/resource evidence. Captured bytes remain
unaccepted until independent validation. There is no legacy-profile widening,
source write, generic process framework or native/quality qualification claim.

Complete source/candidate native decode and host-owned MP4/audio/clock/metadata
comparison precede strict-size private commitment. New markers carry retained
digest pins and reuse existing no-follow/fsync/no-replace primitives. Readback
checks current candidate structure and captured relations without observing
original tools or claiming fresh native qualification. Lossy pixel equivalence,
human quality review, replacement/disposal and public upload stay separate.

November 12 proposed source extension: tool-free profile-aware folder preview
reuses the same discovery owner with an explicit v1/v2 selection, separate request
fingerprint and inventory schema. Pure profile description and preview bypass
mutable application state. They grant no native, replay, candidate, mutation or
physical-reclamation authority. No new codec or implicit profile upgrade is added.

- **Status:** Proposed; source implementation/merge does not ratify or qualify it.
- **Date:** 2026-11-06
- **Issue:** #146

The first video producer remains a typed FFmpeg/ffprobe adapter with a closed
Matroska/FFV1 stream-copy subset. It adds no codec engine, generic process/job
framework or cross-suite orchestrator. Flow owns before/after placement through
released contracts. The historical read-only review/observation APIs stay distinct.

Selected Linux user-manager services and a safe internal exec guard provide
observed cgroup provider-subtree memory limits and aggregate private tmpfs
scratch. Other writable mounts, unavailable/degraded limits and unsupported
hosts refuse. Total Rust host RSS, general escaped-process containment and hard
preemption of host syscalls/parsing are not claimed; these scopes remain explicit.
Resource numbers, exact launch/provider bytes and actual guard receipts bind
candidate evidence. No privileged manager or installation is implicit.

Host-owned independent EBML/payload/timestamp observation and complete source/
candidate decode comparison precede strictly-smaller acceptance. Descriptive or
unknown features refuse. Lossy execution and quality approval remain separate.
Source bytes are read only and re-observed at precommit.

Video uses its own versioned candidate protocol over the existing descriptor,
private staging, no-follow, fsync and no-replace publication primitives. It does
not expand PNG's closed member vocabulary or add replacement/disposal authority.
Partial staging and failed/unconfirmed cleanup stay failures without adoption.

All source/compiler/tests/lint/schema/native/provider/CI qualification remains
deferred by maintainer; no native-supported-host acceptance or release is recorded.

November 12 proposed source extension: the explicit MP4 CLI bypasses mutable
configuration/state and delegates to the same public profile/producer/readback
owners. Fixed serial MP4 folders reuse descriptor discovery under their own
inventory identity. Frozen inputs/tools, immutable starts/results, explicit
bounded continuation and exact store membership stop uncertain work without
replay or adoption. After a durable result, an explicit policy may remove only
the known generated duplicate scratch candidate; originals and retained audit
records remain. A missing cleanup receipt blocks continuation. This extends
source composition only; proposed status, native/quality/release qualification,
replacement/disposal and public-upload boundaries are unchanged.

November 7 source extension: bounded serial folder discovery and per-entry
start/result evidence compose this same producer. A single candidate runs at
a time; failed/unresolved states stop and read-only recovery grants no replay.
See [folder scope](../video-folder-candidates.md). Proposed status, native/host
qualification and the separate future mutation/disposal boundary are unchanged.

November10 proposed source extension: an explicitly selected v2 profile raises
geometry/frame/encoded/decoded and artifact bounds within the same FFV1 stream
copy lane. One internal profile owns admission, source/provider capture,
independent parser/decode and publication/readback limits. V1 wire/fingerprint
meaning and folder defaults remain unchanged; there is no failed-v1 fallback.
The same existing Linux guard owns provider-subtree/scratch evidence. Larger
payload estimates are not full host RSS or native qualification. Distinct v2
request/evidence/marker identities prevent cross-profile relabeling; source
replacement/disposal and broader media remain separate. See [v2 scope](../video-candidate-profile-v2.md). Proposed status is unchanged.
